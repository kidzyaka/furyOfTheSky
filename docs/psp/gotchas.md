# Ловушки PSP: железо, GE, прошивка, тулчейн

Формат записи: **симптом → причина → решение → где проверено.**
«Железо» = PSP-3006 с CFW, «эмулятор» = PPSSPP (macOS, SDL-сборка из Homebrew).

---

## 1. Линковка `pspkernel` → чёрный экран на железе

- **Симптом.** Сборка без ошибок и предупреждений. На PSP после запуска — чёрный экран, консоль не реагирует,
  выключается только удержанием питания. Ни одного кадра, даже отладочный текст не появляется.
- **Причина.** В `target_link_libraries` была указана `pspkernel`. В `libpspkernel.a` лежат заглушки
  импорта **режима ядра**: `ThreadManForKernel`, `LoadExecForKernel`, `UtilsForKernel`,
  `InterruptManagerForKernel`. Линкер разрешил ими `sceKernelCreateCallback`, `sceKernelSleepThreadCB`,
  `sceKernelExitGame`, `sceKernelDcacheWritebackRange` раньше, чем пользовательскими из `libpspuser`.
  Пользовательский модуль (`PSP_MODULE_USER`) не может импортировать библиотеки ядра — заглушки остаются
  неразрешёнными, первый же вызов падает.
- **Как диагностировали (эмулятор, `--log=… -d`):**
  ```
  Importing Module ThreadManForKernel, stubs at 08826e28
  Importing [UNK: 0xe81caf8f] : 08826e28      ← sceKernelCreateCallback
  Importing [UNK: 0x82826f70] : 08826e30      ← sceKernelSleepThreadCB
  Unknown syscall from known HLE module 'LoadExecForKernel': 0x05572a5f   ← sceKernelExitGame
  Encountered bad syscall instruction at 08826e28 (03ffffcc)
  Unknown syscall: Module: '(unknown)' (module: 255 func: 4095)
  ```
- **Решение.** Не линковать `pspkernel` в пользовательских программах. Нужные заглушки
  (`*ForUser`) тулчейн добавляет сам.
- **Проверка без эмулятора:** `strings build/psp/fury | grep ForKernel` — должно быть пусто.
  `tools/smoke_test.sh` проверяет это автоматически.
- **Где проверено.** Причина и исправление — эмулятор. Симптом — железо. Исправление на железе — *ожидает проверки*.

## 2. GE читает память мимо кэша CPU

- **Симптом (ожидаемый).** На железе «мусор» вместо модели/текстуры, мерцание, частично верная картинка;
  в эмуляторе всё хорошо.
- **Причина.** CPU пишет через кэш данных (write-back), GE читает напрямую из памяти. Данные, оставшиеся
  «грязными» в кэше, GE не видит.
- **Решение.** После записи данных, которые будет читать GE (вершины, индексы, текстуры, CLUT), —
  `sceKernelDcacheWritebackRange(ptr, size)` (или `...WritebackAll()`). Сделано в `core::loadFile`.
  Данные, выделенные из списка команд через `sceGuGetMemory`, отдельно сбрасывать не нужно —
  pspgu пишет их сам (так делают примеры SDK).
- **Где проверено.** Не проверено (превентивно, по документации SDK). Эмулятор кэш не моделирует.

## 3. Адреса VRAM: относительные для GU, абсолютные некешируемые для CPU

- `sceGuDrawBuffer`, `sceGuDispBuffer`, `sceGuDepthBuffer` принимают **смещения от начала VRAM** (0, 0x88000…).
- `sceGeEdramGetAddr()` возвращает `0x04000000`. CPU читает/пишет VRAM через **некешируемое зеркало**
  `0x40000000 | (0x04000000 + смещение)` = `0x44000000 + смещение`, иначе увидит устаревшие данные из кэша.
- `pspDebugScreenInitEx(nullptr, …)` сам берёт `0x44000000`; `pspDebugScreenSetOffset(смещение)` — куда писать.
- **Где проверено.** Эмулятор (скриншоты `render/screenshot.cpp` читают кадр так).

## 4. Данные для GE должны жить, пока GE их не прочитал

- Список команд и всё, на что он ссылается (вершины, индексы, матрицы), читается GE **после** возврата из функции.
  Вершины на стеке → мусор.
- **Решение.** Покадровая геометрия — через `sceGuGetMemory(size)` (выделяет прямо в списке команд).
  Постоянные данные — в куче на всё время жизни. Список команд — статический, `alignas(16)`.
- **Где проверено.** Эмулятор (градиент неба через `sceGuGetMemory`).

## 5. Виртуальное пространство GE 4096×4096

- Растеризатор работает в координатах 0..4095. Экран 480×272 ставят в центр:
  `sceGuOffset(2048 − 240, 2048 − 136)`, `sceGuViewport(2048, 2048, 480, 272)`.
- `GU_TRANSFORM_2D` — координаты сразу экранные (0..479, 0..271).
- **Где проверено.** Эмулятор.

## 6. Текстуры: swizzle, CLUT, ширина буфера

- **Swizzle** (`sceGuTexMode(..., swizzle=1)`): текстура хранится блоками **16 байт × 8 строк**, блоки подряд
  слева направо, затем следующая полоса из 8 строк. Для T8 блок = 16×8 текселей. Ускоряет выборку
  (кэш текстур GE — 8 КБ). Реализация: `_swizzle` в `tools/models/fmodel.py` (reshape h/8,8,w/16,16 →
  transpose 0,2,1,3). Каждый мип-уровень свизлится отдельно.
- **CLUT** грузится блоками по 8 записей: для 256 цветов `sceGuClutLoad(32, clut)`.
  CLUT выровнен на 16 байт. `sceGuClutMode(GU_PSM_8888, 0, 0xFF, 0)`.
- **Ширина буфера** (`tbw` в `sceGuTexImage`) кратна 16 байтам. Размеры текстуры — степени двойки, максимум 512.
- **Мипы:** `sceGuTexMode(psm, levels − 1, …)`, `sceGuTexImage(i, w>>i, h>>i, w>>i, ptr)`,
  `sceGuTexLevelMode(GU_TEXTURE_AUTO, 0)`, фильтр `GU_LINEAR_MIPMAP_LINEAR`.
- **T4:** младший полубайт = левый тексель.
- **Где проверено.** Эмулятор (обе ливреи отображаются правильно). Железо — ожидает проверки.

## 7. Освещение — в мировом пространстве

- Источники света задаются в мировых координатах; GE преобразует нормали матрицей модели.
- Для `GU_DIRECTIONAL` «позиция» = направление **на** источник.
- `sceGuLightMode(GU_SEPARATE_SPECULAR_COLOR)` добавляет блик после модуляции текстурой → белый блик
  даже на тёмном камуфляже.
- Цвета во всех API — **ABGR** (`0xAABBGGRR`).
- **Где проверено.** Эмулятор.

## 8. Выход по HOME требует потока, спящего в `*CB`

- Ядро доставляет callback только потоку, который ждёт с обработкой callbacks (`sceKernelSleepThreadCB`,
  `sceKernelDelayThreadCB`…). Поэтому отдельный поток `callbacks` (приоритет 0x11, стек 0xFA0) создаёт
  callback, регистрирует `sceKernelRegisterExitCallback` и засыпает навсегда.
- **Где проверено.** Эмулятор. Железо — ожидает проверки (меню HOME → «Выход»).

## 9. Флаги сборки и память

- **`-G0`** обязателен: загрузчик модулей PSP не поддерживает small data через `$gp`.
- **`PSP_HEAP_SIZE_KB(-1024)`** — куча = вся свободная память минус 1 МБ.
  `create_pbp_file` по умолчанию пишет `MEMSIZE=1` в PARAM.SFO → на моделях 2000+ доступна расширенная память.
  Сколько именно доступно на PSP-3006 — **не измерено**.
- **`THREAD_ATTR_VFPU`** в `PSP_MAIN_THREAD_ATTR` — без него VFPU-инструкции в потоке падают.

## 10. Рабочая папка и пути

- pspsdk при старте делает `chdir` в папку EBOOT (`ms0:/PSP/GAME/FuryOfTheSky/`) → относительные пути работают.
- В PPSSPP при запуске EBOOT вне «карты памяти» эмулятора папка монтируется как `umd0:` — **только чтение**.

## 11. macOS засоряет карту памяти файлами `._*`

- Finder/rsync создают AppleDouble-файлы `._ИМЯ`; в XMB они видны как повреждённые записи.
- **Решение.** `rsync --exclude '._*'` + `dot_clean -m` (в `tools/deploy.sh`).

## 12. Тулчейн pspdev на macOS требует `libmpc` из Homebrew

- **Симптом.** `psp-cmake` падает на проверке компилятора:
  `dyld: Library not loaded: /opt/homebrew/opt/libmpc/lib/libmpc.3.dylib … psp-gcc: internal compiler error: Abort trap: 6 signal terminated program cc1`.
- **Решение.** `brew install libmpc` (уже в `tools/install_toolchain.sh`).
  Проверить все бинарники на недостающие библиотеки:
  `otool -L ~/pspdev/libexec/gcc/psp/*/cc1 | grep /opt/homebrew`.
- **Где проверено.** macOS 27, Apple Silicon.

## 13. `make` из Xcode не перелинковывает изменения «в ту же секунду»

- **Симптом.** Поменяли `target_link_libraries`, `cmake --build` пишет `Built target fury`, но бинарник старый
  (проверка `strings build/psp/fury | grep ForKernel` показывает удалённую библиотеку).
- **Причина.** `/usr/bin/make` (GNU Make 3.81 из Xcode) сравнивает время изменения с точностью до секунды.
  Если `link.txt` и бинарник записаны в одну секунду, бинарник считается актуальным.
- **Решение.** При сомнениях — `rm build/psp/fury && cmake --build build/psp`. На практике проявляется только
  в скриптах, которые пересобирают дважды подряд.
- **Где проверено.** macOS 27, при проверке `tools/smoke_test.sh` на заведомо сломанной сборке.

## 14. `strings … | grep -q` в скриптах с `set -o pipefail`

- **Симптом.** Проверка «есть ли в ELF `ForKernel`» молча не срабатывает, хотя строки есть.
- **Причина.** `grep -q` выходит на первом совпадении, `strings` получает SIGPIPE, `pipefail` делает весь
  конвейер неуспешным → `if` считает, что совпадений нет.
- **Решение.** Сохранять вывод в переменную (`x="$(strings … | grep … || true)"`) и проверять `-n "$x"`.

## 15. Порядок обхода граней: для правосторонних CCW-мешей — `GU_CCW`

- **Факт.** Меши из Blender (обход против часовой стрелки снаружи, правая система координат) с
  `sceGuFrontFace(GU_CCW)` + `GU_CULL_FACE` отображаются правильно; с `GU_CW` — наизнанку.
- **Ловушки.** `GU_TRIANGLE_STRIP` чередует обход: 2D-полоса из 4 вершин теряет один из треугольников —
  рисовать без отсечения. Геометрию, видимую изнутри (купол неба), — тоже.
- **Где проверено.** Эмулятор (software renderer), [ADR 0012](../decisions/0012-backface-culling-ccw.md). Железо — ожидает проверки.

## 16. `GU_SPRITES` работает и в 3D — готовые билборды

- Две вершины `GU_SPRITES` с `GU_TRANSFORM_3D` задают углы прямоугольника, который после проекции рисуется
  выровненным по экрану. Если углы взять как `центр ∓ right·r ± up·r` (векторы камеры), получается
  камеро-ориентированный спрайт за 2 вершины вместо 4–6. Работает с текстурой, туманом, альфа-смешиванием.
- Используется для облаков и солнца.
- **Где проверено.** Эмулятор (software renderer). Железо — ожидает проверки.

## 17. `uint32_t` на PSP — это `long unsigned int`

- **Симптом.** `-Wformat`: `'%u' expects 'unsigned int', but argument has type 'uint32_t' {aka 'long unsigned int'}`.
- **Причина.** В newlib для MIPS PSP `uint32_t` объявлен через `long`. На Mac — через `int`, там предупреждения нет.
- **Решение.** Приводить к `unsigned` для `%u` или использовать `PRIu32` из `<cinttypes>`.

## 18. Детерминизм: не сравнивать и не пересылать структуры через `memcmp`/`memcpy`

- **Симптом.** Тест «одинаковый ввод → побитово одинаковое состояние» проходил с `-O1` и падал в Debug-сборке.
- **Причина.** `memcmp` по всей `FlightState` сравнивает и байты выравнивания после полей `bool` — в них мусор
  со стека. Физика при этом детерминирована.
- **Решение.** Сравнивать поле за полем (float — побитово). Для будущей сети: сериализовать поля явно,
  никогда не слать «сырые» структуры.

## 19. Ближняя плоскость и большие треугольники: дыры в море под камерой

- **Симптом (эмулятор, software renderer, 2026-10-14).** На высоте 14–20 м в нижней части кадра светлая
  «дыра» в океане — видно цвет очистки (дымку). После падения, когда глаз камеры у самой воды, — прямоугольная
  дыра у нижнего края.
- **Причина.** Плитка 320 м под камерой содержит вершины позади камеры. Отсечение по ближней плоскости
  (`GU_CLIP_PLANES`) делает новые вершины на `z = near`, и они проецируются в `смещение/near`: при near = 1 м
  и смещении 16 м это ~4200 px от центра. Это за пределами виртуального экрана GE 4096×4096 ([№5](#5-виртуальное-пространство-ge-40964096)),
  и такой треугольник GE отбрасывает целиком.
- **Решение** ([ADR 0019](../decisions/0019-lighting-graphics.md)):
  - море из двух сеток: мелкая 16 м под камерой, крупная 320 м с дыркой в центре;
  - **ближняя плоскость 3 м**: плитка 16 м укладывается в ~1550 px;
  - камера после падения поднимается над водой.

  Остаточный риск: глаз ниже ~4 м.
- **Где проверено.** Эмулятор (до и после, скриншоты smoke-теста). Железо — ожидает проверки.
- **Обобщение (2026-10-14).**
  - Выбрасывается любой треугольник, у которого вершина, отсечённая ближней плоскостью, проецируется дальше
    ±2048 px от центра. Отсечённая точка лежит на `z = near`, её экранное смещение — `смещение / near × f`
    (f ≈ 236 px при FOV 60°). При near = 3 м это любой треугольник, проходящий мимо камеры дальше ~26 м сбоку.
  - Если каждый треугольник не больше 1/3 своего расстояния до глаза, выброшенные куски целиком за кадром. На этом
    правиле построены кольца моря ([ADR 0040](../decisions/0040-ocean-v2.md)).
  - Для скал и островов, у которых обрыв может оказаться в десятке метров от камеры, правило потребовало бы
    шага ~8 м по всей стене. Вместо этого куски у глаза **отсекаются программно** (`render/guard_clip.h`,
    [ADR 0042](../decisions/0042-sea-stacks-terrain.md)): ближняя плоскость 3,05 м и «защитная пирамида» ±1900 px.
    GE получает только треугольники, которым отсечение не нужно.
  - Host-тест `ge_precision` проверяет геометрию отсечения. Эмулятор (software renderer воспроизводит выброс, см.
    симптом выше): smoke-кадр в ~40 м от обрыва, 145 треугольников отсечено программно, дыр нет. Железо —
    **не проверено**.

## 20. Матрицы в GE — 24-битные float: дрожание вдали от начала координат

- **Симптом (железо, PSP-3006).** Самолёт за камерой начинает «трясти» через некоторое время полёта; чем
  дальше от точки старта, тем сильнее (замечено «на скоростях выше 450–500 км/ч» — просто быстрее улетали).
  На ЖК PSP-3000 дрожащая картинка превращается в «месиво из пикселей».
- **Причина.** Аргумент команды GE — 24 бита. `sceGuSetMatrix` (и всё, что через него: `sceGum*`, `sceGuSetMatrix`)
  отправляет элементы матрицы как `bits >> 8`: 1 бит знака, 8 бит порядка, **15 бит мантиссы**. Перенос 8000 м
  квантуется шагом 0,24 м. Матрицы модели и вида округляются независимо → относительное положение прыгает.
  Проверено дизассемблером: `psp-objdump -d libpspgu.a`, `<sceGuSetMatrix>`: `srl v0,v0,0x8; or v0,v0,t0` (`t0 = 0x3D000000`).
- **Решение.** Рендер относительно камеры — [ADR 0013](../decisions/0013-camera-relative-rendering.md).
  Модель ошибки и проверка — `tests/ge_precision_test.cpp`.
- **Что ещё затронуто тем же ограничением:** любые float-параметры команд (туман, свет, `sceGuTexScale/Offset`) —
  держать их значения умеренными.
- **Где проверено.** Симптом — железо; причина — дизассемблер + численная модель; исправление на железе — ожидает проверки.

## 21. ЖК PSP-3000 и быстрое движение

- У PSP-3000 экран с заметными «чересстрочными» артефактами (полосы через строку) на быстро движущемся
  контрастном изображении. Программно не отключается.
- **Что можно сделать:** держать главный объект неподвижным на экране (см. №20), избегать мелких контрастных
  деталей на быстро движущихся поверхностях (океан у земли), не давать камере мелко дрожать.
- **Где проверено.** Железо (наблюдение автора), меры — ожидают оценки.

## 22. В 2D-режиме (`GU_TRANSFORM_2D`) UV — в текселях, а не 0..1

- **Симптом (ожидаемый).** 2D-спрайт или линия HUD с UV 0..1 показывает один тексель на весь квад.
- **Причина.** В «сквозном» режиме GE не масштабирует координаты текстуры: `u, v` — номера текселей уровня 0.
  В 3D-режиме они нормализованы (0..1) и масштабируются `sceGuTexScale`.
- **Решение.** Для 2D подставлять размеры текстуры: HUD-штрих `0..16` (`fx_line` 16×16), блик линзы `0..64`.
  Float-UV (`GU_TEXTURE_32BITF`) в 2D работают.
- **Где проверено.** Эмулятор (HUD, блик линзы). Железо — ожидает проверки.

## 23. `GU_DIRECT`: GE выполняет список, пока CPU его ещё дописывает

- **Наблюдение (лог PPSSPP, `-d`).** Внутри кадра много раз `sceGeListUpdateStallAddr` и
  `Resuming DL execution at … - stall = …`: pspgu сдвигает адрес остановки по мере записи, и GE рисует начало
  кадра параллельно с работой CPU.
- **Следствия.**
  - Буфер глубины и цвета текущего кадра **нельзя** читать CPU во время построения списка: очистка уже могла
    пройти. Читать готовый кадр — только после `sceGuSync` (в `endFrame` перед сменой буферов, хук `overlay`).
    Так устроена проверка видимости солнца для блика ([ADR 0019](../decisions/0019-lighting-graphics.md)).
  - Данные из `sceGuGetMemory` после того, как на них сослался вызов отрисовки, менять нельзя: GE может уже их
    прочитать.
- **Где проверено.** Эмулятор (лог). На железе поведение pspgu то же — это код библиотеки.

## 24. Аддитивное смешивание + туман GE = «засвеченная дымка»

- **Симптом.** Аддитивные эффекты (пламя, блики, гребни волн) вдали превращаются в светлые пятна цвета дымки.
- **Причина.** Туман GE смешивает цвет фрагмента с цветом тумана *до* блендинга. Аддитивный проход прибавляет к
  кадру уже «затуманенный» цвет, то есть дымку.
- **Решение.** На время аддитивных проходов цвет тумана — **чёрный** (`gfx::setAdditiveFog(true)`): вдали
  эффект плавно гаснет до нуля, а это и есть правильный результат. Для alpha-смешивания туман обычный.
- **Где проверено.** Эмулятор (второй проход моря, пламя).

## 25. GCC 15: `-Warray-bounds` на `std::sort` маленького массива

- **Симптом.** `warning: array subscript 16 is outside array bounds of '…Puff [14]'` из
  `bits/stl_algo.h` при `std::sort` фиксированного массива на 14 элементов с `-O2`.
- **Причина.** Ложное срабатывание: после встраивания вставками GCC не видит, что индекс ограничен `n`.
- **Решение.** Для массивов из десятка элементов — простая сортировка вставками.
- **Где проверено.** psp-gcc 15.2.0.

## 26. Свет в пространстве рендера: точечные источники — относительно камеры

- Источники GE задаются в «мире» — то есть после матрицы модели. В рендере относительно камеры
  ([№20](#20-матрицы-в-ge--24-битные-float-дрожание-вдали-от-начала-координат)) мир сдвинут на позицию глаза.
  Направленным источникам это всё равно, а **позицию точечного источника** нужно передавать как
  `worldPos − renderOrigin()` (сделано в `gfx::setPointLight`), иначе свет форсажа уедет на километры.
- Затухание `sceGuLightAtt(n, a0, a1, a2)`: интенсивность `1/(a0 + a1·d + a2·d²)`, значения — 24-битные float.
- **Где проверено.** Эмулятор (подсветка хвоста на форсаже).

## 27. `int32_t` на PSP — это `long`: `std::clamp(x, -32768, 32767)` не компилируется

- **Симптом.** `error: no matching function for call to 'clamp(int32_t&, int, int)'` — только в PSP-сборке, на Mac
  тот же код собирается.
- **Причина.** Как и в [№17](#17-uint32_t-на-psp--это-long-unsigned-int): в newlib для MIPS `int32_t` — это `long`, а
  литералы — `int`. Шаблон `std::clamp<T>` не может вывести один `T` из двух разных типов.
- **Решение.** Явный аргумент шаблона: `std::clamp<int32_t>(x, -32768, 32767)`.
- **Где проверено.** psp-gcc 15.2.0.

## 28. Звук: `sceAudio` — только 44 100 Гц, выход блокирующий, свой поток

- Канал резервируется `sceAudioChReserve(PSP_AUDIO_NEXT_CHANNEL, samples, PSP_AUDIO_FORMAT_STEREO)`. Число кадров
  должно быть кратно 64 (у нас 1024 ≈ 23 мс). Частота у этих каналов **только 44 100 Гц**: другие частоты
  ресемплирует наш микшер (ADR 0024).
- `sceAudioOutputPannedBlocking(ch, volL, volR, buf)` возвращается, когда железо приняло блок. Это и есть
  часы аудиопотока, поэтому блок нужно успеть смешать за ~23 мс. Громкость `PSP_AUDIO_VOLUME_MAX` = `0x8000`.
- Поток звука должен иметь приоритет **выше** игрового цикла (у нас 0x12 против 0x20), иначе долгий кадр
  оставит звук без данных (треск). Блокирующий вызов отдаёт CPU, так что игре это почти не мешает.
- Импортируется из `libpspaudio`: `sceAudioChReserve`, `sceAudioOutputPannedBlocking`, `sceAudioChRelease`. Все
  три пользовательские (не `*ForKernel`).
- Буферы выровнены на 64 байта, перед выводом делается `sceKernelDcacheWritebackRange`. Это страховка:
  копирует ли драйвер буфер сам или берёт по DMA, **не проверено**.
- Атомарные операции: у Allegrex нет LL/SC. Очередь команд микшера — SPSC на `volatile` индексах с барьером
  компилятора (`std::atomic_signal_fence`), без `std::atomic` RMW.
- **Где проверено.** Эмулятор (PPSSPP: канал 7, блоки по 1024, FPS не упал). Железо — **не проверено**.

## 29. `sceGuScissor(x, y, w, h)`: ширина и высота — но не во всех pspsdk

- **Симптом (2026-10-14, при написании ножниц для меню).** По памяти считалось, что pspsdk
  трактует `w, h` как правый нижний **край** (в старых версиях `scissor_end = w − 1`). С такой трактовкой
  область `(x0, y0, x1, y1)` в нашем `gfx::clip` обрезала бы снизу не по краю, а на `y0 + y1` —
  то есть почти никак; на скриншотах это не видно, когда ниже нарисована плашка.
- **Причина.** В установленной версии (`~/pspdev`, сборка `pspdev-macos-latest-arm64`, GCC 15.2) функция
  считает конец как `x + w − 1`, `y + h − 1` — дизассемблированный `sceGuScissor.o` из `libpspgu.a`:
  `addu a2,a0,a2; addiu a2,a2,-1`. Комментарий в `pspgu.h` («width/height») теперь правдив.
- **Решение.** `gfx::clip(x0, y0, x1, y1)` (`src/render/draw2d.cpp`) передаёт `x1 − x0, y1 − y0`.
  Полноэкранные ножницы `(0, 0, 480, 272)` верны при обеих трактовках — поэтому старый код не ломался.
  Проверить версию: `psp-ar x libpspgu.a sceGuScissor.o && psp-objdump -d sceGuScissor.o`.
- **Где проверено.** Дизассемблирование библиотеки (тулчейн автора). Эмулятор/железо — поведение GE
  от этого не зависит, только смысл аргументов.

## 30. `std::floor` на Allegrex — вызов libm

- **Симптом (эмулятор, 2026-10-14).** Построение списка моря (CPU-затенение ~6 тыс. вершин) — 9,5 мс вместо
  ожидаемых 3–4.
- **Причина.** `std::floor` / `floorf` в newlib для MIPS — вызов функции с ветвлениями, не инструкция. В цикле по
  вершинам (хэш-шум, таблица синуса) это заметная доля кадра.
- **Решение.** Отбрасывание дробной части через `static_cast<int>` с поправкой для отрицательных — в `world::fastSin`,
  таблицах шума моря, `world::Terrain` (`sectorAt`). Вместе с таблицей пятен ветра и слиянием прохода блеска
  ушло ~4,6 мс.
- **Где проверено.** Эмулятор (счётчик `L` в отладочном углу). Железо — не измерено.

## 31. Индексированные треугольники: GE трансформирует каждый индекс

- **Наблюдение.** Тот же меш списком `GU_TRIANGLES` с индексами стоит ~3 трансформации с освещением на
  треугольник. Повторно использованные вершины не берутся из кэша. По данным сообщества разработчиков PSP, кэша
  трансформированных вершин у GE нет. **На железе не проверено.**
- **Решение.** Регулярные сетки — лентами `GU_TRIANGLE_STRIP` с индексами, ряды сшиты вырожденными
  треугольниками. Острова ([FTR1](../formats/ftr1.md), теперь [FTR2](../formats/ftr2.md)) — 1,5 индекса на треугольник вместе с юбками
  вместо 3,4. Отладочный счётчик `V` в углу — сколько индексов (вершин для GE) ушло на рельеф за кадр.
- **Где проверено.** Не проверено. Сравнить на железе FPS одного и того же кадра у списка и у ленты — открытый
  вопрос ([roadmap](../roadmap.md)).
- **С 2026-10-15** лентами рисуются также кольца моря и слоя облаков (`render/grid_mesh.*`, 2,7× меньше индексов) и
  меши FSM4 (`tools/models/stripify.py`; Су-35С — 2,0 индекса на треугольник). Профилирование по частям кадра (строка
  `Z` отладочного угла) — способ проверить это на железе.

## 32. `GU_SPRITES` в 3D — всегда прямоугольник по осям экрана

- **Симптом (железо, 2026-10-14, отзыв автора).** В развороте облака «наклоняются вместе с камерой»: освещённые
  верха и тёмные основания поворачиваются вслед за креном.
- **Причина.** Спрайт `GU_SPRITES` задаётся двумя углами. GE проецирует их и закрашивает прямоугольник,
  выровненный по экрану. Как ни считай углы в мире, при крене камеры картинка спрайта остаётся «ровно по экрану».
- **Решение.** Всё, что должно стоять ровно относительно горизонта (облака — `render/clouds.cpp`), рисуется
  четырёхугольником из 2 треугольников с осями «вид × вертикаль мира». Это 6 вершин против 2, отсюда бюджет на
  число облаков. Круглые частицы (дым, искры) можно оставлять спрайтами.
- **Где проверено.** Железо (симптом, отзыв автора), эмулятор (smoke: облака в развороте стоят по горизонту).

## 33. Двойная буферизация с vsync: 34 мс кадра = 20 FPS, а не 29

- **Симптом (железо, 2026-10-15, отзыв автора).** FPS прыгает между 30 и 20: «в небе 30+, со скалами 20». Промежуточных
  значений почти нет.
- **Причина.**
  - Готовый кадр ждал `sceDisplayWaitVblankStart` и переключался `sceGuSwapBuffers`;
  - пока он не показан, рисовать следующий некуда (второй буфер на экране);
  - кадр чуть длиннее 33,3 мс пропускает второй vblank и ждёт третьего — 50 мс, 20 FPS.
- **Решение.** Тройная буферизация (`gfx::presentFrame`):
  - кадр ставится в очередь `sceDisplaySetFrameBuf(…, PSP_DISPLAY_SETBUF_NEXTFRAME)`, рисование идёт в третий буфер;
  - ждём vblank, только если прошлый поставленный кадр ещё не показан (`sceDisplayGetVcount` не сменился);
  - адрес для `sceDisplaySetFrameBuf` абсолютный: `sceGeEdramGetAddr()` + смещение;
  - для рисования — `sceGuDrawBufferList` в начале кадра;
  - VRAM: третий буфер 512×272×4 = 544 КБ.
- **Где проверено.** Эмулятор (smoke: меню и вылет, скриншоты из нужного буфера). Железо — **не проверено**.


## 34. `sceGuStart` возвращает буфер рисования из `sceGuDrawBuffer`, а не из `sceGuDrawBufferList`

- **Симптом (эмулятор, 2026-10-15).** В smoke-кадре вылета нет ни моря, ни самолёта, ни HUD: только цвет очистки и
  отладочный угол. Строка `Z` показывает, что это был кадр профилирования (каждый 64-й при включённой отладке).
- **Причина.**
  - `sceGuStart(GU_DIRECT, …)` при ненулевой ширине кадра заново шлёт GE адрес буфера рисования из внутреннего
    `gu_draw_buffer` pspgu (исходник pspsdk `sceGuStart.c`). Этот адрес задаёт только `sceGuDrawBuffer` — у нас один
    раз в `init()`, буфер 0;
  - `sceGuDrawBufferList` шлёт команды напрямую и `gu_draw_buffer` **не меняет**;
  - с тройной буферизацией (№33) буфер меняется каждый кадр через `sceGuDrawBufferList`. После перезапуска списка
    посреди кадра (`gfx::profileSync`: `sceGuFinish` → `sceGuSync` → `sceGuStart`) остаток кадра уходит в буфер 0;
  - на железе это кадр с дырами плюс мусор в буфере, который в этот момент на экране или в очереди: мелькание раз в
    ~2 с при включённой отладке.
- **Решение.** После каждого `sceGuStart` посреди кадра — снова `sceGuDrawBufferList(GU_PSM_8888, g_drawBuffer, …)`
  (`gfx::profileSync`). Общее правило: если буфер рисования меняется через `sceGuDrawBufferList`, любой
  `sceGuStart` надо сопровождать им же.
- **Где проверено.** Эмулятор (software renderer: кадр 47 smoke-теста пустой до исправления, с морем и HUD после).
  Железо — **не проверено** (мелькание не замечали, но отладочный угол включают редко).
